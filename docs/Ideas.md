# Идеи ускорения запуска и меню

Дата анализа: 14.10.2026.

Цель: максимально сократить время запуска, задержки навигации и применения действий без потери функций, надёжности и производительности работающего Zapret/Telegram.

Ниже сохранён исходный анализ. Реализация и измерения выполнены отдельным этапом 14.10.2026; актуальный статус каждой идеи приведён сразу после этого абзаца. Ссылки на номера строк в исходном анализе относятся к коду до переноса меню.

## Область анализа

- Открытие `service.bat`: до UAC, после UAC, до первого экрана и до готовности ввода.
- Возвраты в главное меню, настройки, статус, диагностика и подменю Telegram.
- Ручной запуск через `strategies/*.bat` → `utils/run-preset.bat`.
- Установка/перезапуск службы через `utils/manage-service.ps1`.
- Запуск Telegram: проверка состояния, ожидание готовности и упаковка исполняемого файла.

Автоматический старт уже установленной службы Windows — отдельный сценарий: он не проходит через меню и повторный рендер конфигурации. Ускорение `service.bat` само по себе не ускорит обработку трафика или автозапуск двигателя. Эти показатели следует проверять отдельно.

## Что уже сделано и должно сохраниться

- Сообщение `Starting Zapret 2 NEXT...` выводится до тяжёлых проверок (`service.bat:25`). Это улучшает обратную связь, но не означает готовность меню к вводу.
- Логирование и первый статус Telegram объединены в `manage-logs.ps1 -MenuBootstrap`; до повышения прав и при ожидающем восстановлении Telegram пропускается (`service.bat:28–37`).
- Первый статус Telegram использует `-Fast`: точечный COM-запрос задачи, получение SID через native API и предварительную проверку наличия TCP listener (`utils/telegram-control.ps1:96–158`). Проверки владельца при этом сохранены.
- Главный экран сохраняет последний статус Telegram между переходами (`service.bat:138–149`). Предлагать просто «закэшировать Telegram» недостаточно: это уже есть.
- Автоматическая проверка обновлений запускается в фоне один раз на открытие меню; ввод читает локальный результат. ETag и блокировка параллельных проверок уже реализованы (`service.bat:104–108`, `utils/update-release-core.ps1:134`).
- До меню выполняется необходимое восстановление обновления; ошибка восстановления блокирует дальнейшую работу (`service.bat:50–59`).
- Конфигурация службы проверяется движком до остановки работающей службы; есть откат, блокировки и защита чужих процессов/установок (`utils/service-control.ps1:118`).

## 01. Замеры по этапам и контроль отсутствия регрессий

Добавить в отдельной будущей работе измерения монотонным `Stopwatch` и внешний стенд, который фиксирует появление приглашения и фактическую обработку ввода. Обычный `durationMs` журнала не охватывает старт PowerShell до инициализации логирования (`utils/session-log.ps1:319`), поэтому одного журнала недостаточно.

Раздельные метрики:

- Старт → видимое сообщение; старт → запрос UAC; подтверждение UAC → первый экран; подтверждение → готовый ввод. Время решения пользователя по UAC не включать в машинную задержку.
- Enter → начало действия; конец действия → снова готовый ввод; Back/Cancel → главный экран.
- Рендер, dry-run, остановка, старт двигателя, подтверждение успешного старта, закрытие окна — отдельные интервалы.
- CPU, число дочерних процессов, пиковая и установившаяся память, файловые операции; отдельно нагрузка за минуту открытого бездействующего меню и после его закрытия.
- Для изменений запуска — сетевые проверки и отсутствие ухудшения задержки/пропускной способности после старта. Скорость обработки пакетов не выводить из скорости интерфейса.

Сравнивать медиану и p95 на одинаковом состоянии системы; прогретые запуски повторять сериями, холодные измерять отдельно после перезагрузки/восстановления VM. Не называть первый запуск в серии гарантированно холодным. Стенд не должен самостоятельно отключать Defender, чистить системные кэши или менять приоритет работающего двигателя.

## 02. Лёгкий путь чтения меню и настроек

**Основание:** при каждом `ReadMenuChoice` загружаются `update-release-core.ps1`, `update-release-state.ps1` и журнал (`utils/update-release.ps1:15–17`). Core дополнительно подключает управление службами, Telegram, IPSet и общие зависимости (`utils/update-release-core.ps1:3–7`). Для чтения цифр и локального баннера большая часть этих определений не нужна. Это загрузка кода, а не выполнение всех функций обновления.

**Идея:** вынести ввод, чтение баннера и минимальные общие функции в небольшой модуль. Загружать Prepare/Apply/Recover, архивирование и Windows-операции только для соответствующего действия. Аналогично отделить `SetSetting`/`ToggleCheck` от полного updater, сохранив единые функции атомарной записи и блокировки. Убрать повторное dot-source одних зависимостей в рамках одной операции, если замеры подтвердят пользу.

**Условия:** сохранить `111`, появление уведомления во время набора, Backspace, кириллицу, перенаправленный stdin/stdout, логирование выбора и контракт кодов 100–115/211. Ошибка helper не должна превращаться в выбор пункта 1. Состав recovery-копии и проверки комплектности релиза потребуется обновить при разделении файлов.

## 03. Один процесс PowerShell на всё меню

**Основание:** BAT каждый раз запускает PowerShell для `ReadMenuChoice`, действий и цветного вывода. Уже используется достаточно сложный PowerShell-ввод; стоимость нового процесса повторяется при возвратах.

**Идея:** оставить `service.bat` совместимым входом, а основной цикл, отображение, чтение выбора и лёгкие действия держать в одном PowerShell 5.1-процессе. Загружать модули по требованию один раз. Это наиболее перспективный путь для радикального устранения повторных затрат, но более крупный, чем идея 02.

**Условия:** сначала выделить функции из CLI-скриптов: существующие `exit`, `$script:*`, `$LASTEXITCODE`, глобальные настройки консоли и контекст журнала нельзя бездумно переносить в общий процесс. Контекст операции должен восстанавливаться после вложенных действий; блокировки, handles и COM-объекты должны освобождаться. Update worker и сценарии, которым нужна изоляция, оставить отдельными процессами. При обновлении старый host должен действительно завершаться и освобождать установку перед заменой файлов.

Постоянный процесс существует только пока открыто меню: не добавлять службу, watcher или задачу автозапуска. Проверить отсутствие роста памяти после сотен переходов. Сравнить RAM/CPU с исходной реализацией; уменьшение числа запусков не гарантирует меньшую память автоматически.

## 04. Цветной вывод без запуска PowerShell на каждую строку

**Основание:** `:green`, `:yellow`, `:red` выполняют `powershell -NoProfile -Command Write-Host` (`service.bat:617–624`). Quick check и некоторые настройки вызывают их несколько раз подряд.

**Идея:** в варианте 03 печатать через уже работающий host. Для сохранения BAT рассмотреть вывод блока сообщений одним helper-вызовом либо поддерживаемые терминалом VT-последовательности.

**Условия:** сохранять цвет в поддерживаемых консолях, читабельный вывод при перенаправлении и совместимый вариант для консолей без VT. Проверить cmd.exe, Windows Terminal, Windows 10/11, восстановление цветов и обработку специальных символов в сообщениях. Не ускорять вывод ценой потери текста ошибок.

## 05. Сократить повторную работу журнала

**Основание:** каждый `Initialize-ZapretLog` пересоздаёт/проверяет каталоги, пишет метаданные и lease, вызывает retention всех сессий под общим gate (`utils/session-log.ps1:303–339`). Каждый из шести стартовых снимков настроек отдельно проходит запись события и обработку pending-очереди (`utils/manage-logs.ps1:29–36`, `utils/session-log.ps1:214–226`). Инициализация допускает ожидание gate до 5000 мс — это верхний предел при конкуренции, а не постоянная задержка каждого запуска.

**Идея:** отделить создание/подключение сессии от старта операции. Полное обслуживание retention выполнять при границах сессии и экспорте, а для действий использовать лёгкое подключение. Стартовый снимок писать одной группой под одной блокировкой, сохраняя отдельные события и их схему. Не переписывать `session.json`, если его состояние уже нужное. Конкретную частоту обслуживания выбрать после проверки сценариев прерывания.

**Условия:** не терять события при аварии, UAC, параллельных меню и экспорте; сохранить распознавание прерванных операций, защиту живых сессий, лимиты размера и последние пять сессий. Не заменять устойчивую запись буфером только в RAM. Проверки путей/reparse points и фильтрация приватных данных остаются. Если отложенное обслуживание нарушает эти гарантии, оптимизировать сам проход, а не откладывать его.

## 06. Сократить цепочку до и после UAC

**Основание:** обычный запуск создаёт журнал, запускает PowerShell для `Start-Process -Verb RunAs`, затем ещё один для Finish/Handoff; elevated BAT повторяет Start и снимки настроек (`service.bat:25–46`, `utils/manage-logs.ps1:27–48`). Bootstrap также делает до трёх CIM-запросов для определения владельца через оболочки `FOR /F` (`utils/manage-logs.ps1:18–24`).

**Идея:** объединить подготовку, повышение прав и handoff в одном bootstrap-процессе. В варианте 03 отказаться от лишней промежуточной оболочки `FOR /F`; при возможности получать parent PID без запуска CIM provider. При присоединении elevated-стороны не повторять неизменившуюся подготовку без необходимости.

**Условия:** сохранить запись отказа/ошибки UAC, один SessionId, корректный PID и время старта владельца; не путать короткоживущий cmd с владельцем меню. Настройки между двумя стадиями могут измениться: повторный снимок нужен при изменении. Telegram по-прежнему относится к пользователю рабочего стола при вводе учётных данных другого администратора. Не откладывать recovery до разрешения действий меню.

## 07. Распространить быстрый статус Telegram на остальные экраны

**Основание:** `-Fast` используется в bootstrap, но `manage-telegram.ps1` для компактного статуса и перерисовки подменю вызывает обычный `Get-ZapretTelegramStatus` (`utils/manage-telegram.ps1:23,43`). После выхода в главный экран запускается ещё один процесс проверки (`service.bat:438`).

**Идея:** использовать общий быстрый механизм получения состояния и в этих точках после подтверждения эквивалентности. В рамках одного действия один результат может обслуживать заголовок, подробный вывод и журнал. Возвращать актуальное состояние из Telegram-меню в основной host без дополнительного старта helper; для BAT понадобится отдельный структурированный канал результата.

**Условия:** сохранить все состояния, включая `OTHER_FOLDER`, `PORT_CONFLICT`, `UNMANAGED`, `CONFIG_MISSING`, `ERROR`; не считать существование задачи/порта доказательством владения. При наличии listener быстрый путь всё ещё использует полную проверку — эффект для RUNNING может быть меньше, чем для DISABLED. Перед изменением задачи, процесса или порта выполнять свежие необходимые проверки, независимо от кэша заголовка.

## 08. Один снимок состояния для одного отображения

**Основание:** `:read_status` каждый раз вызывает `sc.exe`, `reg query` с `findstr` и чтение mode-файлов (`service.bat:138–158`). Quick check отдельно получает компактный Telegram-статус и затем запускает подробный `manage-telegram.ps1 -Action Status` (`service.bat:559–563`).

**Идея:** собрать снимок один раз на отображение/действие. В едином PowerShell-host использовать API служб и реестра без цепочек cmd → reg → findstr. Для настроек применять контролируемую инвалидацию после изменений; дешёвое чтение маленьких файлов оптимизировать только после более дорогих участков.

**Условия:** не вводить бесконечный кэш службы: она может остановиться вне меню. Explicit Check Status всегда обновляет данные. Пауза пользователя между экранами означает, что прежний снимок мог устареть. Настройки могут меняться вторым меню или вручную; проверять актуальность при возврате и перед действием. Предпочтительно объединять дубликаты внутри одной операции, не ослабляя свежесть данных между операциями.

## 09. Меньше файловой работы во время ввода

**Основание:** `Read-ReleaseMenuChoice` проверяет клавиатуру с паузой 25 мс, баннер — каждые 250 мс. `Get-ReleaseMenuBanner` повторно читает JSON, а при доступном обновлении ещё repository/version и сравнивает версии (`utils/update-release.ps1:29–82`). Даже если автообновление выключено, цикл проверки локального баннера остаётся.

**Идея:** внутри одного ожидания хранить разобранный результат; перечитывать его при изменении файла, а неизменные repository/version — при соответствующей инвалидации. Сохранить короткий интервал проверки клавиш. При варианте 03 рассмотреть уведомление о завершении своего worker, сохранив проверку обновлений файла от других процессов и резервный polling.

**Условия:** сравнение только timestamp/size может пропустить замену с совпавшими атрибутами; предусмотреть периодическую полную сверку или версию записи. Чтение должно сохранять `FileShare.Delete`, чтобы не блокировать атомарную замену `check.json`. Не отключать уже доступное уведомление при выключении авто-check без отдельного решения о поведении. Не добавлять постоянно работающий watcher ради нескольких чтений малого файла без доказанной выгоды.

## 10. Снизить конкуренцию фоновой проверки при открытии

**Основание:** background Check стартует непосредственно перед новым процессом `ReadMenuChoice` (`service.bat:104–109`). Сеть уже не блокирует меню напрямую, но оба процесса могут одновременно загружать общие скрипты, обращаться к диску и журналу.

**Идея:** сначала сделать готовым ввод, затем запускать лёгкий worker из цикла меню; вместе с идеей 02 уменьшить его зависимости. В одном host не переносить сетевую проверку на поток ввода. Сравнить первый ввод при авто-check on/off и при медленной/недоступной сети.

TTL для `CheckedUtc` или backoff между повторными открытиями — только отдельная условная идея: сейчас ETag уменьшает ответ, но не отменяет HTTP-запрос на каждом новом открытии. TTL изменит момент обнаружения релиза, поэтому не включать его в обязательное ускорение «без изменения функционала». Ручной пункт 12 и проверка перед установкой должны оставаться свежими.

## 11. Не читать весь IPSet для ответа «есть ли запись»

**Основание:** `utils/render-config.ps1:238–240` читает весь `lists/ipset-all.txt`, фильтрует строки, материализует массив и проверяет `Count > 0`. Это делается даже при режимах `none`/`any`. В исследованной рабочей копии файл занимает 557 599 байт; размер у пользователей может отличаться.

**Идея:** для `loaded` читать поток до первой строки, не соответствующей текущему условию комментария/пустоты, затем закрывать reader. Для `none`/`any` не сканировать файл, если результат не используется. Здесь требуется проверка наличия записи, а не её подсчёт.

**Условия:** сохранить семантику пустых строк/комментариев, кодировку и обработку ошибок чтения. Полная валидация IPSet в обновлении и движке сохраняется. Проверить пустой файл, BOM, только комментарии, запись в конце и большой заполненный файл.

## 12. Один рендер — два варианта конфига

**Основание:** ручной запуск дважды запускает `render-config.ps1`; служба дважды вызывает renderer в своём PowerShell-процессе (`utils/run-preset.bat`, `utils/service-control.ps1:81–93`). Шаблоны, режимы, пользовательские списки и IPSet обрабатываются повторно. В текущем renderer `DryRun` добавляет `--wf-dup-check=0` и `--dry-run` к готовому содержимому (`utils/render-config.ps1:301–304`).

**Идея:** выделить функцию построения конфигурации, один раз получить согласованный снимок входов и сформировать из него рабочий и проверочный варианты. Для службы это сокращает повторный рендер, но не «два лишних процесса»: там renderer уже вызывается внутри текущего host. Для ручного запуска исчезает и второй запуск PowerShell.

**Условия:** dry-run должен проверять именно тот рабочий вариант, который будет применён. Сохранить порядок аргументов, переводы строк, пути, создание недостающих пользовательских файлов, debug/intercept-параметры и журнал. Держать согласованность под существующей моделью блокировок; внешнее изменение входов перед применением требует обнаружения/повторной проверки. Не вводить постоянный кэш успешно проверенного конфига, который переживает изменение Lua, списков или двигателя.

## 13. Один координатор ручного запуска

**Основание:** `utils/run-preset.bat` последовательно вызывает отдельные PowerShell для логирования, двух рендеров, dry-run, запуска и завершения. BAT выполняет предварительные проверки конфликтов, а `invoke-winws.ps1:76–80` снова проверяет службы и процессы под блокировкой.

**Идея:** свести последовательность в PowerShell-координатор и переиспользовать функции renderer/engine/logging. Публичные BAT-лаунчеры и CLI оставить совместимыми. Предварительные запросы объединить, но финальную проверку конфликта перед запуском оставить внутри критической секции.

**Условия:** не dot-source существующие CLI с `exit` напрямую; сначала отделить функции. Сохранить коды ошибок, показ stdout/stderr и timeout dry-run. Не удерживать нерекурсивный `engine-operation.lock` при вызове функции, которая снова пытается его открыть. Reentrant bundle mutex работает в контексте потока: перенос на другой runspace требует явного проектирования. Валидация предшествует замене текущего процесса, чужие процессы не завершаются.

## 14. Разобрать фиксированные ожидания

**Основание:** ручной запуск ждёт `StartupWaitSeconds=3` после старта двигателя (`utils/invoke-winws.ps1:16,141`); служба ждёт ещё 3 секунды после Running (`utils/service-control.ps1:35–43`); восстановление ручного процесса при обновлении также ждёт 3 секунды (`utils/update-release-state.ps1:96–104`). После сообщения об успехе BAT дополнительно делает `timeout /t 4 /nobreak`.

**Идея:** сначала отделить задержку закрытия окна от готовности двигателя. Четыре секунды влияют на длительность лаунчера, но двигатель в это время уже запущен. Можно рассмотреть закрытие по клавише/настраиваемую длительность, сохранив возможность прочитать результат; это изменение UX, а не ускорение сети.

Трёхсекундные окна нельзя просто удалить или сократить: они ловят ранний выход. Для будущего ускорения исследовать достоверный сигнал готовности и механизм сохранения проверки раннего сбоя. Наличие PID или состояние SCM Running сами по себе не заменяют нынешний контроль. Без эквивалентного механизма оставить эти окна, а ускорять подготовку до них. Не выдавать ранний успех и не отпускать транзакцию/откат раньше необходимой проверки.

## 15. Пропускать только доказанно пустое изменение

**Основание:** повторный выбор текущего Game/Voice/fake-профиля всё равно пишет настройку и переходит к refresh (`service.bat:298–415`). Refresh вновь создаёт candidate, проверяет его и при согласии перезапускает службу.

**Идея:** обнаруживать отсутствие изменений и избегать ненужной записи/пересборки там, где состояние действительно уже применено. Учитывать отдельно сохранённые настройки и конфигурацию работающего процесса.

**Условия:** совпадение mode-файла недостаточно: пользователь мог раньше отказаться от рестарта, изменить списки/шаблоны или обновить компоненты. Повторный выбор может намеренно применить отложенную настройку. Сохранить явный способ повторного применения/рестарта и существующий смысл Install Service. Без доказательства отсутствия изменений выполнять прежний путь.

## 16. Удешевить ожидание старта Telegram

**Основание:** каждый проход `Wait-ZapretTelegramReady` получает задачу, listeners и процессы, затем ждёт 300 мс (`utils/telegram-control.ps1:454–469`). Процессы запрашиваются и при отсутствии listeners.

**Идея:** пока listener отсутствует, не запрашивать список процессов без необходимости; использовать проверенные быстрые способы чтения задачи/наличия порта. Когда появился listener, выполнить полную проверку PID, SID, пути, аргументов и адреса. Сравнить затраты запросов и интервала опроса прежде, чем уменьшать паузу.

**Условия:** сохранить общий timeout, проверку владельца задачи, обнаружение чужого listener и ошибки старта. Быстро появившийся открытый порт не является доказательством готовности именно нашего прокси. Не ускорять проверку исключением хеширования бинарника перед Enable.

## 17. Не компилировать native helper повторно без необходимости

**Основание:** определение `ZapretTelegram.NativeShell` компилируется через `Add-Type -TypeDefinition`, если тип ещё отсутствует (`utils/telegram-control.ps1:13–48`). Защита уже предотвращает повторную компиляцию внутри одного процесса, но не между отдельными PowerShell-запусками.

**Идея:** сначала получить выигрыш от единого host. Если компиляция остаётся заметной частью холодного старта, рассмотреть небольшую сборку helper на этапе релиза с загрузкой готового типа.

**Условия:** оценить цену нового бинарного артефакта, проверок целостности, совместимости PowerShell 5.1/.NET и обновления/recovery. Не загружать DLL из пользовательского временного кэша. Сохранить выбор desktop SID, проверку SessionId и ошибки доступа. Не переходить к отдельному скомпилированному менеджеру целиком без измеренного остаточного ограничения: объём переноса существенно больше.

## 18. Эксперимент с упаковкой Telegram

**Основание:** сборка использует PyInstaller `--onefile --windowed --noupx` (`packaging/build-telegram.py:59–65`). Стоимость загрузки упакованного приложения нужно отделить от проверок PowerShell и сетевой готовности.

**Идея:** на отдельной тестовой сборке сравнить текущий вариант с `onedir`: холодный старт до listener, тёплый рестарт, размер поставки, I/O и память. Это гипотеза для измерения, не утверждение о найденной основной причине задержки.

**Условия:** сохранить отсутствие требования установленного Python, все библиотеки/сертификаты и offline/self-test. Новый layout потребует согласования manifest/hash-check, упаковки релиза, обновления и rollback; все runtime-файлы должны проверяться. В итог принимать только при заметном выигрыше без ухудшения доставки и восстановления. Меньшее число проверок целостности не считать оптимизацией.

## Что не считать допустимым ускорением

- Удаление dry-run, проверок владельца, блокировок, SHA256, восстановления или отката.
- Отключение журналирования, потеря ранних ошибок либо сокращение истории сессий.
- Выдача устаревшего/непроверенного состояния как актуального успешного результата.
- Одновременное выполнение операций, меняющих службу, конфигурацию, Telegram или файлы обновления, ради меньшего времени ожидания.
- Отключение Defender, ослабление UAC, изменение системных политик или добавление автозапуска фонового «ускорителя».
- Сокращение таймаутов, задержек анти-DPI, числа фейков или сетевых проверок стратегии ради красивой цифры старта меню.
- Обязательная установка PowerShell 7/Python ради меню, которое сейчас работает с системным PowerShell 5.1.

## Проверки при реализации

Для будущих изменений использовать существующие `utils/validate-session-log.ps1`, `utils/validate-telegram.ps1`, `utils/validate-release-update.ps1`, `utils/validate-stability.ps1`, `utils/validate.ps1` и `packaging/test-release-console.py`. Дополнять тесты конкретными нарушаемыми контрактами, а не копиями реализации. На этапе первичного анализа наборы не запускались; после реализации результаты записаны в `PERFORMANCE.md`.

Матрица приёмки:

- Windows 10/11, Windows PowerShell 5.1, cmd/Windows Terminal, русский/английский вывод, перенаправленный ввод, пути с пробелами и поддерживаемыми специальными символами.
- Обычный запуск с UAC, уже elevated, отказ UAC, другой администратор; запуск после обновления, pending recovery/cleanup, ошибка recovery.
- Telegram disabled/stopped/running, чужая папка/порт, повреждённый config, недоступный Scheduler; начальный статус совпадает с подробной проверкой при неизменном окружении.
- Служба отсутствует/остановлена/работает, отложенные настройки, изменение извне, два меню одновременно, чужой ручной двигатель.
- Все пункты 0–15 и `111`, неверный выбор, быстрый ввод до полной отрисовки, Backspace и цифры, набранные во время появления уведомления; ошибка helper не запускает действие.
- Offline/медленная сеть, пустой/повреждённый cache, обновление cache во время ввода; действия меню не ждут сетевой проверки.
- Рендеры всех пресетов и режимов эквивалентны, dry-run сохраняется; ранний выход двигателя, rollback, timeout и отказ записи дают прежний безопасный результат.
- Журнал/экспорт/прерванная сессия, недоступная папка логов, retention, отсутствие секретов; после закрытия меню не остаётся новых фоновых помощников.
- После каждого этапа повторить релевантные замеры: улучшение целевой задержки не принимается за счёт ухудшения p95, постоянной нагрузки, утечек памяти или поведения работающего Zapret/Telegram.
