# Подготовка релизов

Инструкции для сопровождающих проекта. Пользовательский запуск описан в [README](../README.md).

## Бета-тестирование

Бета-канал — добровольная проверка будущей версии до стабильного релиза. Бета-версия публикуется как обычный GitHub **Pre-release** и не заменяет последнюю стабильную версию.

### Как принять участие

1. Откройте [все Releases](https://github.com/Dunterbabochka/zapret2-next/releases) и выберите версию с пометкой **Pre-release**, например `v0.5.0-beta.1`.
2. Скачайте `zapret2-next-vX.Y.Z-beta.N.zip` и `release-sha256.txt`. Не скачивайте автоматически созданный **Source code ZIP**.
3. [Сверьте SHA256](#проверка-sha256) и распакуйте beta в отдельную папку. Не копируйте её поверх стабильной установки.
4. Запустите `utils/START BETA TEST.bat` от имени администратора и пройдите Compatibility Wizard.
5. Проверьте Discord Web/App, Voice в обе стороны, демонстрацию экрана, YouTube и восстановление прежнего состояния Zapret.
6. Создайте [Beta report](https://github.com/Dunterbabochka/zapret2-next/issues/new?template=beta-report.yml). Итоговый ZIP находится в `runtime\compatibility-results`.

> [!WARNING]
> Диагностический ZIP может содержать IP-адреса, порты, PID, временные метки, локальные пути и подробные сетевые логи. Перед публикацией обязательно проверьте вложение и отправляйте только те данные, которыми готовы поделиться. Не публикуйте raw packet captures, токены или cookies.

Если beta мешает работе, закройте её процессы, удалите beta-папку и продолжайте использовать стабильную версию. Не устанавливайте beta как службу до успешной ручной проверки.

### Как опубликовать beta

Владельцу проекта достаточно создать и отправить prerelease-тег:

```powershell
git tag -a v0.5.0-beta.1 -m "Zapret 2 NEXT v0.5.0-beta.1"
git push origin v0.5.0-beta.1
```

Теги с суффиксом `-alpha`, `-beta` или `-rc` автоматически:

- проходят полную валидацию;
- собираются в единый пользовательский ZIP;
- получают `utils/START BETA TEST.bat` и краткую инструкцию;
- публикуются как открытый GitHub Pre-release вместе с `release-sha256.txt`.

Стабильные теги без prerelease-суффикса по-прежнему создают draft для финальной ручной проверки.

## Проверка SHA256

В Release публикуется:

```text
release-sha256.txt
```

Пример проверки архива в PowerShell:

```powershell
Get-FileHash .\zapret2-next-vX.Y.Z.zip -Algorithm SHA256
```

Сравните полученное значение с хэшем из `release-sha256.txt`.

Закреплённая версия движка и контрольные суммы бинарников находятся в [`ENGINE_VERSION`](../ENGINE_VERSION). GitHub Actions проверяет SHA256 `winws2.exe`, `WinDivert.dll`, `WinDivert64.sys`, `cygwin1.dll` и `killall.exe` при push и pull request.

## Сборка

Из корня проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\utils\build-release.ps1 -Version 0.4.3
powershell -NoProfile -ExecutionPolicy Bypass -File .\utils\build-release.ps1 -Version 0.5.0-beta.1 -Beta
```

Стабильная версия должна совпадать с `.service/version.txt`. Сборщик сохраняет ZIP, распакованную папку и `release-sha256.txt` в `dist`. Это воспроизводимые результаты сборки, а не рабочие данные основной установки. Папку можно удалить, если её копии не используются и архивы не нужны.

Перед выпуском выполните [проверки Windows](MANUAL_TEST.md) и тесты автоматического отчёта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\utils\validate-support.ps1
```

## Тестирование обновления без публикации релизов

Запустите `powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-release-update.ps1`. Нужен Python только для разработки. Проверка поднимает сервер на `127.0.0.1`, скачивает настоящие тестовые ZIP, заменяет файлы во временных установках и аварийно завершает дочерние тестовые процессы после шагов замены. Службы, задачи и запуск движка подменены; отдельный dry-run проверяет выбранный конфиг настоящим движком. Тест `cmd.exe` использует собственную скрытую консоль и не вводит ничего в пользовательские окна.

Проверка включена в Validate и Release CI на Windows PowerShell 5.1 с обязательным dry-run настоящего движка (`-RequireNativeEngine`). Локально этот шаг пропускается, если Windows-сессия не повышена; остальные проверки продолжаются. Она не создаёт теги или GitHub Releases. Материалы остаются в `runtime/release-update-tests-*`; в журнале теста сохраняется итоговое число проверок.

Для ручного теста настоящих служб и Telegram используйте отдельную Windows 10/11 VM:

1. Выполните `powershell -NoProfile -ExecutionPolicy Bypass -File packaging/prepare-release-update-lab.ps1`.
2. Запустите локальный сервер командой, которую напечатает сценарий, и откройте указанную тестовую установку `installed/service.bat`.
3. Установите стратегию, выберите нестандартные настройки и включите Telegram. Проверьте обновление через `111`, сохранение настроек и прокси, запуск после перезагрузки и остановленное состояние службы.
4. Изменяя `scenario.json` в папке лаборатории, проверьте `mode: unavailable`, `bad-hash` и `truncated`; при подготовке старая версия должна продолжать работать.

Сценарий лаборатории только создаёт файлы. Он не устанавливает службы и не запускает прокси. Тестовые версии 9.9.0/9.9.1 и адаптер локального HTTP существуют только в лабораторных копиях; их нельзя публиковать как пользовательский релиз.

## Проверка журнала сессий

`powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-session-log.ps1` проверяет настоящий экспорт, параллельные записи, ротацию, прерывание процесса, повреждённый JSONL, занятые файлы и ошибки записи. Тестовые данные находятся в `runtime/log-tests-*`. Приватные тестовые значения не должны появляться в отправляемых журналах и ZIP. Проверки выполняются на Windows PowerShell 5.1 в Validate и Release; интеграция с обновлением проверяется локальным HTTP-сервером существующего теста обновлятора, без GitHub Releases.

Схема журнала — `schemaVersion: 1`, архива — `zapret2-next.session-logs`. Любое новое событие или поле сначала добавляется в разрешённый набор `session-log.ps1` и проверку отсутствия приватных значений. В журнал нельзя передавать сообщения исключений, произвольные строки или вывод команд. Идентификаторы сессии и операции обновления сохраняются в транзакции как необязательные поля `LogSessionId` и `LogOperationId`; транзакции прежних версий продолжают поддерживаться. Ядро журнала копируется в защищённый recovery-каталог вместе с обновлятором.

В CI ссылки проверяются обязательно (`-RequireLinks`); локальная Windows-сессия без нужных прав может пропустить создание symlink. Экспортёр `manage-logs.ps1` также копируется в recovery: из корня установки его вызывают с `-Root .`, если обычное меню повреждено.

Событие имеет случайный `eventId`: повторное слияние очереди после прерывания не создаёт дублей, а действия с одинаковыми UTC и ID операции остаются разными событиями. Старые записи без `eventId` читаются без дедупликации. При конкуренции используются файлы `pending-*.jsonl` в `runtime/log-state/<session>`; готовый экспорт повторно проверяет и объединяет их с двумя сегментами журнала. Каждый сегмент ограничен 3 МиБ, очередь — 2 МиБ, сокращённый `SESSION.txt` — 900 КиБ.

## Проверка запуска и меню

`utils/validate-startup.ps1` проверяет меню настроек, отмену/подтверждение, paired dry-run, потоковую проверку IPSet, контексты журнала, локальный cache и native helper в disposable-копии. Реальные службы и задачи Telegram не изменяются. Набор запускается в Validate и Release под Windows PowerShell 5.1.

`packaging/benchmark-startup.py` измеряет реальный ввод и возвраты через скрытую консоль; `packaging/benchmark-telegram-layout.py` сравнивает экспериментальные сборки без изменения поставляемого runtime. Методику и границы проверки см. в [PERFORMANCE.md](PERFORMANCE.md). Сравнения скорости выполнять последовательно, отдельно от сборки и тяжёлых validation-наборов.
