# Запуск и меню: изменения и проверка

14.10.2026. Меню перенесено в один PowerShell 5.1 host, публичные BAT-входы и вспомогательные CLI сохранены. Навигация, цветной вывод, настройки и Telegram больше не создают новый PowerShell на каждый переход. Обновление, длительная диагностика и действия, которым нужна изоляция, остаются отдельными процессами.

## Реализация

- `utils/menu.ps1` управляет bootstrap/UAC, главным экраном, подменю и жизненным циклом сессии. Состояние службы/настроек обновляется при каждом возврате. Fast Telegram status сохраняет проверки принадлежности задачи, процесса и порта.
- `utils/menu-input.ps1` и `utils/release-info.ps1` читают ввод и локальное уведомление без полного updater. Метаданные проверяются каждые 250 мс; полная сверка каждые 2 секунды обнаруживает даже замену cache с одинаковыми size/timestamp. Проверка обновлений остаётся фоновой, без TTL.
- `utils/run-preset.ps1` и `utils/engine-control.ps1` объединяют ручной запуск. Конфликты проверяются до подготовки и повторно под launch lock; только свой процесс может заменяться после успешного dry-run.
- `render-config.ps1 -ValidationOutput` строит рабочий и проверочный файл за один проход. IPSet сканируется только до первой значимой строки. Полная проверка списка/движка сохранена.
- Журнал записывает стартовый снимок группой и переиспользует аудит внутри host. Новые процессы и recovery обнаруживают прерванные операции. Вложенные действия сохраняют отдельные operation ID и восстанавливают контекст меню.
- Release builder компилирует `bin/zapret-native.dll`, добавляет его SHA256 в каталог, а загрузчик проверяет хеш перед исполнением. В source checkout/recovery предусмотрена inline-компиляция того же кода.
- Worker обновления принимает атомарный marker с PID/временем старта и ждёт завершения именно прежнего host. Старый текстовый marker `released` остаётся совместимым.

## Измерения

Warm console benchmark выполняется на этой машине в disposable-копии. Запросы состояния служб/Telegram заменены границами теста; автоматический network check выключен. Это сравнение накладных расходов интерфейса, а не холодного запуска, UAC или сетевой производительности. Во время итогового сравнения другие validation/build задачи не запускаются.

Семь запусков каждого варианта, по десять переходов и две секунды простоя. Итоговые серии сохраняются в `runtime/startup-baseline-final.json` и `runtime/startup-after-final.json`.

| Показатель | До, медиана / p95 | После, медиана / p95 |
| --- | ---: | ---: |
| Готовность ввода | 1991 / 2120 мс | 1084 / 1160 мс |
| Возврат из диагностики | 874 / 948 мс | 60 / 61 мс |
| Выход | 1231 / 1463 мс | 237 / 278 мс |
| CPU за 2 секунды простоя | 46,9 / 93,8 мс | 15,6 / 62,5 мс |
| RSS процессов консоли (без стенда) | 134,2 / 135,7 МиБ | 153,0 / 153,3 МиБ |

Медианное открытие ускорилось примерно в 1,84 раза, возврат — в 14,5 раза, выход — в 5,2 раза. Для возврата сначала берётся медиана десяти действий каждого запуска; таблица сравнивает семь таких серий. p95 на семи наблюдениях равен максимуму и не является надёжной оценкой редких задержек. Стенд дополнительно сохраняет отдельные переходы и их общий `back_events_ms` для следующих серий. Это локальный результат, а не обещание тех же абсолютных значений на каждой машине.

У persistent host есть измеренная цена: примерно 19 МиБ дополнительного working set, пока окно открыто. Он сохраняет загруженные библиотеки и контекст вместо завершения helper после каждого действия. Поэтому утверждать отсутствие любого роста ресурсов нельзя. Работающий двигатель и прокси не перенесены в host; окно можно закрыть после настройки. Рост RSS после первых переходов включает загрузку/JIT библиотек; для проверки утечки сравниваются установившиеся участки длинной серии.

Дополнительная серия из 300 переходов (`runtime/startup-soak.json`) показала стабилизацию working set: после прогрева/GC с 75-го по 300-й переход RSS держался примерно в пределах 104,7–105,6 МиБ. Это не исчерпывающая проверка всех действий, но линейного роста на пути Diagnostics → Back не наблюдалось.

```powershell
python packaging/benchmark-startup.py --runs 7 --navigation-rounds 10 --idle-seconds 2 --output runtime/startup-after-final.json
```

Для baseline используется отдельная копия исходников до изменений через `--source`. Стенд не запрашивает UAC, не меняет реальные службы/Telegram и не выполняет действия установки. Ввод отправляется в собственную скрытую консоль, не на рабочий стол.

## Telegram: сравнение упаковки

Сборка выполнена в отдельном `runtime/telegram-layout-venv` с версиями из `packaging/telegram-requirements.txt`. Семь запусков frozen self-test для каждого варианта:

| Показатель | onefile | onedir |
| --- | ---: | ---: |
| Медиана warm self-test | 1866 мс | 927 мс |
| p95 (на 7 измерениях — максимум) | 3527 мс | 1168 мс |
| Размер каталога | 15 527 297 байт | 33 453 182 байт |

В этот интервал входят загрузка frozen runtime, импорты и self-test. Он не доказывает скорость до готового listener или работоспособность аккаунта/сообщений/звонков. Стандартная поставка остаётся onefile: выигрыш onedir сопровождается увеличением размера примерно в 2,15 раза; переключение поставки требует VM-проверки установки, обновления и отката всей структуры.

```powershell
runtime/telegram-layout-venv/Scripts/python.exe packaging/benchmark-telegram-layout.py --runs 7
python packaging/build-telegram.py --layout onedir --output runtime/telegram-onedir-test
```

Экспериментальная сборка не переписывает `bin/telegram`, рабочий manifest или корневой SHA256-каталог. Каждая сборка сохраняет полный список хешей собственных файлов.

## Проверки

Проверяются PS 5.1 parser, все 396 комбинаций конфигурации, эквивалентность paired dry-run, меню настроек/подтверждения/отмены, вложенные контексты журнала, отсутствующий cache и замена с совпавшими атрибутами, контроль выхода host, корректный и повреждённый native helper.

Существующие наборы проверяют сбои установки/движка/отката, Telegram lifecycle/владельца, журнал и экспорт, HTTP/архивы/аварийное прерывание обновления и реальную консоль с вводом во время уведомления. `validate-startup.ps1` добавлен в validation/release CI. Тестовая упаковка релиза собирается локально в `runtime/startup-release`; релиз не публикуется.

Локально прошли: 396 конфигураций основного validator, 76 новых startup/menu contracts, 49 stability checks, 85 journal checks, 94 Telegram lifecycle checks и 1673 update checks с настоящим консольным вводом. Собранный архив дополнительно прошёл Quick validation; packaged native helper загрузился после проверки SHA256.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-startup.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-stability.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-session-log.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-telegram.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File utils/validate-release-update.ps1
```

## Границы проверки

На этой машине не выполнялись реальные установки/перезапуски службы, изменения Telegram, UAC под другим администратором, загрузка драйвера, холодные перезагрузки и замеры трафика. Native winws2 dry-run и тесты ссылок, которым требуются недоступные права, отмечаются как skip. Для выпуска остаётся матрица Windows 10/11 из `MANUAL_TEST.md`.

Трёхсекундное наблюдение успешного запуска сохранено. Пропуск refresh по совпавшему mode, TTL обновлений и автоматический переход поставки на onedir не включены: для них не доказана эквивалентность требуемого поведения. Поддержка измерения/эксперимента и безопасные части соответствующих идей реализованы.
